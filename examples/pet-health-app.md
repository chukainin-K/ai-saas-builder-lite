# Example: Pet Health App

## 入力

```text
ペットの健康状態を記録し、通院履歴やワクチン予定を管理できるアプリを作りたい。
```

## Orchestrator Agent: 作業分解

### アイデア概要

犬や猫などのペットについて、日々の健康状態、通院履歴、投薬、ワクチン予定を一元管理するアプリ。

### 前提

- 主な対象は個人の飼い主とする
- 最初のMVPでは動物病院との連携は行わない
- 医療判断は提供せず、記録とリマインダーに集中する
- 不足情報は仮説として扱う

### Agentへの指示

Research Agentには、想定ユーザー、課題、既存代替手段、差別化、MVP検証仮説、リスクの整理を依頼する。

Developer Agentには、Research結果をもとに、MVP要件、技術スタック、データモデル案、開発タスク一覧の作成を依頼する。

# Research Agentの調査結果

## 1. アイデア概要

ペットの健康記録、通院履歴、ワクチン予定をまとめて管理し、飼い主が必要な情報を忘れず確認できるアプリ。

## 2. 想定ユーザー

| ユーザー層 | 特徴 | 主な利用動機 |
| --- | --- | --- |
| 犬や猫を飼っている個人 | 通院、予防接種、日々の体調変化を管理したい | 記録漏れや予定忘れを減らしたい |
| 複数匹を飼っている家庭 | ペットごとに予定や履歴が分かれる | 誰がいつ何をしたか整理したい |
| 高齢ペットの飼い主 | 通院頻度や投薬管理が増える | 体調変化を継続的に把握したい |

## 3. 解決する課題

| 課題 | 現在の困りごと | 重要度 |
| --- | --- | --- |
| 記録が分散する | 紙の診察券、メモアプリ、カレンダーに情報が分かれる | 高 |
| ワクチンや薬の予定を忘れる | 次回予定を自分で管理する必要がある | 高 |
| 体調変化を振り返りにくい | 食欲、体重、症状の推移が残っていない | 中 |
| 家族間で共有しにくい | 誰が通院したか、薬を飲ませたかが分かりづらい | 中 |

## 4. 既存代替手段

| 代替手段 | 使われる理由 | 不足しやすい点 |
| --- | --- | --- |
| 紙の健康手帳 | 動物病院で渡されることがある | 検索、通知、共有が難しい |
| カレンダーアプリ | 予定通知ができる | 健康記録や通院詳細と結びつきにくい |
| メモアプリ | 自由に記録できる | ペットごとの整理やリマインダーが弱い |
| 表計算シート | 複数項目を管理できる | スマホでの継続入力に手間がかかる |

## 5. 差別化ポイント

- ペットごとに健康記録、通院履歴、ワクチン予定をまとめられる
- 次回ワクチンや投薬予定をリマインダーとして扱える
- 日々の体調メモを通院前に振り返りやすくする
- 医療判断ではなく、飼い主の記録負担を減らすことに集中する

## 6. MVP検証仮説

| 仮説 | 検証方法 | 成功条件 |
| --- | --- | --- |
| 飼い主はペットごとの健康記録をスマホで残したい | 5から10名に試用してもらう | 1週間で3回以上記録される |
| ワクチン予定の通知は継続利用の理由になる | 通知機能の利用率を見る | 登録ユーザーの50%以上が予定を1件以上登録 |
| 通院履歴の整理は高齢ペットの飼い主に特に価値がある | 高齢ペットの飼い主にヒアリング | 通院前に履歴を見返したいという回答が多い |
| 複数匹管理は差別化になり得る | 複数匹ユーザーの利用行動を見る | 2匹以上登録するユーザーが一定数いる |

## 7. リスク

| リスク | 内容 | 対応方針 |
| --- | --- | --- |
| 医療アドバイスと誤解される | アプリが診断するものと受け取られる可能性 | 記録管理アプリであることを明記する |
| 入力が面倒で続かない | 日々の記録が負担になる | 入力項目を最小限にする |
| 通知が多すぎる | リマインダーが煩わしくなる | 予定ベースの通知に限定する |
| 家族共有の権限が複雑になる | MVPで実装すると工数が増える | 初期版では共有をMVP外にする |

## 8. Research Agentの結論

MVPでは、ペットごとの基本情報、健康メモ、通院履歴、ワクチン予定リマインダーに集中するのが妥当です。動物病院連携、診断支援、家族共有は価値があり得ますが、初期検証では後回しにします。

# Developer AgentのMVP要件

## 1. MVPの目的

飼い主がペットごとの健康情報、通院履歴、ワクチン予定を迷わず記録し、必要なタイミングで見返せる状態を作る。

## 2. 対象ユーザー

- 犬や猫を飼っている個人
- 複数匹を飼っている家庭
- 高齢ペットの通院や投薬を管理したい飼い主

## 3. 主要機能

| 機能 | 内容 | 優先度 |
| --- | --- | --- |
| ユーザー登録、ログイン | 飼い主ごとにデータを管理する | Must |
| ペット登録 | 名前、種類、誕生日、メモを登録する | Must |
| 健康メモ | 日付、体重、食欲、症状メモを記録する | Must |
| 通院履歴 | 診療日、病院名、診療内容、費用メモを記録する | Must |
| ワクチン予定 | ワクチン名、予定日、通知有無を登録する | Must |
| ダッシュボード | 直近の予定と最近の記録を表示する | Should |

## 4. 非機能要件

- セキュリティ: ユーザーごとにデータを分離し、他ユーザーの記録を参照できないようにする
- パフォーマンス: 個人利用の記録表示が1から2秒以内に完了することを目指す
- 運用: 初期は低コストで運用できるマネージドサービスを使う
- 拡張性: 将来の家族共有や画像添付に備え、ペット単位でデータを紐づける

## 5. 技術スタック

| 領域 | 技術 | 理由 |
| --- | --- | --- |
| Frontend | Next.js | 画面とAPIを同一プロジェクトで作りやすい |
| Backend | Next.js API Routes | MVPでは別バックエンドを立てずに実装できる |
| Database | PostgreSQL | ユーザー、ペット、記録のリレーション管理に向く |
| Auth | Supabase Auth | 認証とDBをまとめて扱いやすい |
| Hosting | Vercel | Next.jsとの相性がよく初期公開しやすい |

## 6. データモデル案

| テーブル | 主な項目 | 用途 |
| --- | --- | --- |
| users | id, email, created_at | 飼い主アカウント |
| pets | id, user_id, name, species, birthday, note | ペット基本情報 |
| health_logs | id, pet_id, logged_at, weight, appetite, symptoms, note | 日々の健康記録 |
| visit_logs | id, pet_id, visited_at, clinic_name, summary, cost, note | 通院履歴 |
| vaccine_schedules | id, pet_id, vaccine_name, scheduled_at, reminder_enabled, completed_at | ワクチン予定 |

## 7. MVP外にするもの

- 動物病院との連携
- 医療診断、症状判定AI
- 家族共有、複数ユーザー権限
- 画像添付
- 決済、有料プラン

| T-002 | P0 | Supabaseプロジェクト設定 | 認証とDB接続が動作する |

- 他ユーザーのペット情報を参照できない
- スマホで主要操作が完了できる
- ワクチン予定と通院履歴がペットごとに正しく紐づく

- 画像アップロード

# Orchestratorの最終まとめ

## 1. 統合結論

このアイデアは、ペットの健康情報が紙、メモ、カレンダーに分散する課題を解決する記録管理アプリとしてMVP化するのが適しています。

初期版では、医療判断や動物病院連携には踏み込まず、飼い主が継続して使える「ペットごとの記録と予定管理」に集中します。

## 2. MVP方針

MVPの中心価値は、以下の3つです。

- ペットごとに健康情報をまとめられる
- 通院履歴をあとから見返せる
- ワクチンや通院予定を忘れにくくする

## 3. 最初に作るべき機能

| 優先度 | 機能 |
| --- | --- |
| Must | 認証 |
| Must | ペット登録 |
| Must | 健康メモ |
| Must | 通院履歴 |
| Must | ワクチン予定 |
| Should | ダッシュボード |
| Should | 通知または予定確認 |

## 4. 技術方針

個人開発や小規模チームで作る前提なら、Next.js、Supabase、PostgreSQL、Vercelの構成が扱いやすいです。MVPではバックエンドを分離せず、Next.js内で画面とAPIをまとめる方針が現実的です。

## 5. 主なリスク

| リスク | 対応 |
| --- | --- |
| 医療アドバイスと誤解される | 記録管理アプリであることを明記する |
| 入力が続かない | 入力項目を最小限にする |
| 通知が煩わしい | 予定ベースの通知に限定する |
| 機能が増えすぎる | 家族共有や画像添付はMVP外にする |

## 6. 次にやること

1. 主要画面を5画面程度に絞ってワイヤーフレームを作る
2. SupabaseでDBテーブルと認証を準備する
3. ペット登録、健康メモ、通院履歴、ワクチン予定のCRUDを実装する
4. 5から10名の飼い主に試用してもらい、記録頻度と継続意向を確認する

## 7. Orchestrator Agentの結論

Lite版の設計としては、記録管理とリマインダーに集中したMVPが最も現実的です。Pro版に拡張する場合は、家族共有、画像添付、動物病院向け共有、詳細な通知設計、収益化設計を別Agentで扱うと拡張しやすくなります。
